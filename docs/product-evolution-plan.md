# Prismath 产品与技术演进计划

> 文档状态：规划基线
>
> 编写日期：2026-09-25
>
> 适用项目：`prismath` 数学模型可视化工具箱

## 1. 文档目的

本计划解决项目当前的四个核心问题：

1. 默认 UI 偏向参数面板，缺少沉浸式体验；
2. 不同模型被迫使用相同的三栏布局和控制方式；
3. 用户缺少从“不了解模型”到“能够自由探索”的交互引导；
4. Tkinter 在连续场、高频交互和 GPU 可视化方面存在上限，Mandelbrot 仍会出现卡顿。

本计划的原则是：**保留已经稳定的数学内核，重构体验层和渲染层，不一次性推倒整个项目。**

---

## 2. 产品方向

### 2.1 新的产品定位

项目从“数学模型参数面板”演进为：

> 一个通过操作、观察和实验帮助用户理解数学模型的交互式数学实验室。

用户不应该先面对一张复杂的参数表，而应该先看到模型的现象，然后逐步理解参数、规则和结果。

### 2.2 三种工作模式

所有模型不再默认展示完整控制面板，而是进入以下三种模式之一：

| 模式 | 目标用户 | 默认界面 | 主要内容 |
| --- | --- | --- | --- |
| 引导模式 | 第一次接触模型的用户 | 沉浸式画布 + 单步提示 | 概念、观察任务、交互练习 |
| 自由探索 | 已理解基本规则的用户 | 沉浸式画布 + HUD | 缩放、拖动、播放、编辑、即时反馈 |
| 实验室模式 | 需要研究和比较的用户 | 画布 + 可展开控制台 | 参数扫描、批量实验、曲线、导出 |

三种模式共享同一模型内核和同一实验状态，但展示的控件数量不同。

### 2.3 设计原则

- **现象优先**：先让用户看到变化，再解释参数。
- **直接操作优先**：能在画布上完成的操作，不要求先打开表单。
- **渐进披露**：高级参数默认隐藏，按需展开。
- **模型决定交互**：连续场、网格、粒子和统计模型可以拥有不同舞台。
- **计算与渲染分离**：数学结果不依赖具体 UI，交互预览不阻塞高质量计算。
- **每一步都可回退**：缩放、参数和引导进度都支持撤销或重新开始。

## 3. 当前架构评估

### 3.1 应保留的部分

当前项目的以下部分已经形成较好的基础，不应在第一阶段重写：

```text
prismath/models/<model>/model.py   纯计算内核
prismath/models/<model>/spec.py    参数、动作、元数据和 handler
prismath/registry.py               模型自动发现与注册
prismath/spec.py                   ModelSpec / ParamSpec / ActionSpec
tests/                             模型正确性、金样本、视图冒烟和基准
```

现有 `ModelSpec` 已能统一描述参数、动作、模型元信息和后端调用入口；现有测试也为迁移提供了必要护栏。

### 3.2 应停止继续扩大的部分

以下方向不应继续作为长期主架构：

- 让所有模型都继承同一个三栏 Tk 布局；
- 在 `ui/tk/kit/` 中继续增加越来越多的模型特例 mixin；
- 把引导文案、教学状态和交互规则直接写进具体视图类；
- 让 Web UI 只作为 Tk 的简单镜像；
- 通过不断提高 Mandelbrot 的 numpy 计算量来解决交互卡顿。

### 3.3 目标架构

```text
                    ┌────────────────────────┐
                    │  Web / Canvas / WebGL   │  主 UI
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │   Experience Layer     │  引导、模式、会话状态
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │   Render Scheduler     │  预览、分块、取消、缓存
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │   Model Core           │  numpy / 纯数学模型
                    └────────────────────────┘

                    Tk / CLI 为保留后端和降级路径
```

### 3.4 推荐目录演进

第一阶段不移动现有模型目录，只新增以下模块：

```text
prismath/
├── experience/
│   ├── __init__.py
│   ├── spec.py          # 引导步骤、模式、模型能力声明
│   ├── session.py       # 当前用户会话和完成状态
│   └── transitions.py   # 步骤完成条件与状态转换
├── render/
│   ├── __init__.py
│   ├── protocol.py      # RenderRequest / RenderResult / Tile
│   ├── scheduler.py     # 单活动任务、取消、generation
│   ├── cache.py         # 预览和 tile 缓存
│   └── metrics.py       # 计算、编码、上传和显示耗时
└── ui/
    ├── web/
    │   ├── server.py
    │   └── static/
    │       └── app/     # 后续拆分 TypeScript/前端模块
    └── tk/              # 兼容后端，逐步减少新增功能
```

## 4. 模型能力和视觉范式

### 4.1 新增能力描述

在保留现有 `ModelSpec` 字段的前提下，逐步增加能力描述。第一版可以用不可变数据类：

```python
RenderCapabilities(
    visual_kind="field",              # field / grid / particles / geometry / chart
    supports_zoom=True,
    supports_pan=True,
    supports_play=False,
    supports_editing=False,
    supports_gpu_preview=True,
    default_mode="immersive",
    advanced_controls=True,
)
```

能力描述只描述“模型能做什么”，不描述“具体放在哪个像素位置”。布局属于 UI 外壳，模型视图只声明交互和数据需求。

### 4.2 第一批视觉范式

| 范式 | 模型 | 主要交互 | 默认模式 |
| --- | --- | --- | --- |
| 连续场 | Mandelbrot | 平移、缩放、探针、色带 | 引导 / 沉浸 |
| 离散网格 | Life Game、渗流 | 播放、单步、点击编辑 | 引导 / 沉浸 |
| 粒子系统 | N-body | 暂停、跟踪、拖动、时间轴 | 沉浸 |
| 几何统计 | Buffon Needle | 播放采样、观察收敛 | 引导 / 实验室 |
| 图表实验 | 扫描、批量统计 | 参数比较、曲线、导出 | 实验室 |

新增模型时先选择视觉范式，再实现该范式的适配器；不要默认选择一个“大而全”的页面模板。

## 5. 体验设计方案

### 5.1 通用页面结构

```text
┌────────────────────────────────────────────┐
│ 返回       模型名称              模式 / 帮助 │  顶部浮层
│                                            │
│                                            │
│              沉浸式主舞台                    │
│                                            │
│        当前提示 / 关键数值 / 交互反馈         │  HUD
│                                            │
│  手势提示       [重新开始] [控制台] [下一步]   │
└────────────────────────────────────────────┘
```

控制台以抽屉或浮层形式出现，而不是永久占据左右两栏。只有实验室模式才默认打开详细参数。

### 5.2 引导模式

引导流程由模型声明，不由通用 UI 硬编码。例如 Mandelbrot 的首个版本：

| 步骤 | 目的 | 用户动作 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 认识复平面取景 | 查看画布和坐标 | 用户进入步骤 |
| 2 | 观察逃逸 | 点击一个明显亮点 | 得到一个逃逸点说明 |
| 3 | 观察慢逃逸区域 | 点击边界附近 | 采样点的迭代次数高于阈值 |
| 4 | 理解缩放 | 对边界进行缩放 | 完成一次缩放并保持视图 |
| 5 | 发现细节 | 自由探索一个新结构 | 用户主动平移或再次缩放 |
| 6 | 进入实验室 | 打开参数或跳过引导 | 会话进入自由探索 |

引导步骤至少包含：

```python
GuideStep(
    key="inspect-escape",
    title="先找一个会逃逸的点",
    prompt="点击亮色区域，看看这个点用了多少次迭代才逃逸。",
    explanation="颜色表示逃逸速度，而不是集合内外的简单二分。",
    allowed_actions=("inspect",),
    completion="point_inspected",
)
```

### 5.3 自由探索模式

自由探索模式只保留：

- 主画布；
- 少量关键指标；
- 当前手势提示；
- 撤销、重置和控制台入口；
- 必要的加载、清晰度和精度状态。

不能把所有参数都放到 HUD 中。HUD 只呈现当前操作有帮助的信息。

### 5.4 实验室模式

实验室模式承接现有项目的优势：

- 完整参数表单；
- 批量统计；
- 参数扫描；
- 曲线和结果表；
- 随机种子；
- 数据导出；
- 可复制的实验配置。

现有 Tk 三栏界面可以先保留作为实验室模式的兼容实现。

## 6. 技术路线选择

### 6.1 结论

推荐：**Web 前端作为主 UI，Canvas/WebGL 作为主渲染方式，Python 本地服务保留模型内核；Tk 作为后备后端。**

暂不建议第一步引入 Tauri，也不建议先把所有模型迁移到 Flet。

### 6.2 原因

- 浏览器对画布、动画、输入事件和全屏布局支持更成熟；
- WebGL 适合 Mandelbrot、连续场和粒子系统的高频绘制；
- 前端可以本地维护拖动、缩放和播放状态，减少 Python 往返；
- Python 继续负责 numpy、统计、模型正确性和高质量结果；
- 未来如果需要桌面安装，可以在 Web 版本稳定后再用 Tauri 打包；
- Tk 不需要被删除，它仍然适合低依赖运行、开发调试和简单模型。

### 6.3 后端通信的演进

当前 HTTP action 接口可以保留为兼容接口。新接口分为两类：

```text
GET  /api/models                 模型目录和能力
GET  /api/model/<key>/experience 引导流程
POST /api/model/<key>/action      低频动作和统计
POST /api/render                  高质量渲染任务
GET  /api/render/<id>             任务状态或结果
```

第一版不要求立即引入 WebSocket。可以先用短轮询验证流程；当 tile 渲染和实时进度稳定后，再引入 SSE 或 WebSocket。

## 7. Mandelbrot 专项性能方案

### 7.1 目标

目标不是让 Python 在任何深度都达到 60 FPS，而是区分交互预览和高质量计算：

| 场景 | 目标 |
| --- | --- |
| 拖动过程中 | 立即显示低清预览，不阻塞输入 |
| 滚轮缩放 | 画面立即跟随光标，旧结果不跳回 |
| 松开鼠标后 | 后台逐步变清晰 |
| 高质量渲染 | 可取消、可显示进度、只采用最新请求 |
| 深度超过 float64 可靠范围 | 明确提示精度限制，而不是静默输出错误图形 |

### 7.2 第一阶段：修复现有调度器

当前 generation 机制能丢弃过期结果，但不能阻止旧线程继续计算。应先完成：

1. `escape_counts()` 接收可选取消事件；
2. 每隔固定迭代批次检查取消；
3. 每个视图最多保留一个活动渲染任务；
4. 新请求到达时取消旧任务；
5. 将计算、数组转 RGB、PPM 编码、Tk 上传分开计时；
6. 记录最近一次渲染的像素数、迭代数、计算耗时和显示耗时。

### 7.3 第二阶段：分块渲染

将整图渲染改为 tile 渲染：

```text
请求产生 generation
  ↓
先显示低分辨率预览
  ↓
按视口中心优先生成 128×128 或 256×256 tile
  ↓
主线程 / 浏览器逐块替换图像
  ↓
请求变化时取消全部旧 tile
```

每个 tile 必须绑定以下信息：

```text
generation
viewport
tile 坐标
resolution
iterations
palette
```

这样可以避免旧视图的 tile 在新视图中错位显示。

### 7.4 第三阶段：WebGL 交互预览

WebGL shader 负责：

- 每个像素对应复平面坐标；
- 并行迭代；
- 输出逃逸时间；
- 运行色带映射；
- 响应拖动和缩放。

Python/numpy 负责：

- 高质量最终图；
- 统计量；
- 面积估计；
- 教学说明使用的数据；
- CLI 和无 GPU fallback。

### 7.5 精度边界

普通模式使用 float64 和 GPU 预览。超过可靠范围后显示：

```text
当前已接近普通浮点精度边界。
画面仍可用于探索，但像素级数学精度可能下降。
```

只有在普通交互体验稳定后，才评估 perturbation 或任意精度深度缩放，不把它列入第一期范围。

## 8. 分阶段实施计划

### Phase 0：基线和决策冻结

**目标：** 保证重构不会破坏现有数学结果。

工作项：

- 确认当前未提交改动的归属并保留；
- 固化现有模型金样本和性能基线；
- 增加 Mandelbrot 的交互性能记录方式；
- 明确 Web UI 为新主方向，Tk 不再增加复杂交互特性；
- 选定 Mandelbrot、Life Game、N-body 作为前三个垂直切片。

完成标准：

- 现有测试可以重复运行；
- 有默认取景、缩放取景和深放大取景的基准数据；
- 后续每次改动都能区分“模型变慢”与“界面变慢”。

### Phase 1：能力描述和体验协议

**目标：** 让模型能够声明视觉范式、交互能力和默认模式。

工作项：

- 新增 `RenderCapabilities`；
- 新增 `GuideStep`、`ExperienceSpec`；
- 为 Mandelbrot 编写第一份引导配置；
- 为 Life Game 和 N-body 添加最小能力声明；
- API 返回能力和体验描述；
- 不改变现有 `handler`、`factory` 和 CLI 行为。

完成标准：

- 同一模型可以被识别为 `field`、`grid` 或 `particles`；
- UI 不需要通过模型 key 判断是否显示缩放、播放或编辑按钮；
- 引导内容可以脱离具体 Tk 类独立测试。

### Phase 2：Web 沉浸式外壳

**目标：** 建立新的默认用户体验，但先只接 Mandelbrot。

工作项：

- 重组 `ui/web/static` 的页面结构；
- 实现全屏舞台、HUD、抽屉、模式切换；
- 实现引导步骤显示、完成和跳过；
- 实现统一快捷键、鼠标手势和触摸预留接口；
- 将实验室参数面板放入抽屉；
- 保留当前 Web API 和 generic fallback。

完成标准：

- 用户首次进入 Mandelbrot 不会先看到完整参数面板；
- 用户可以完成引导、跳过引导并进入自由探索；
- 参数控制台可以打开、关闭，不丢失当前取景和状态；
- 刷新页面后可以恢复模型和模式，至少恢复默认取景。

### Phase 3：渲染调度器和 Mandelbrot 交互性能

**目标：** 先解决任务生命周期和预览策略，再引入 GPU。

工作项：

- 新增通用 `RenderRequest`、`RenderResult` 和取消协议；
- 实现单活动任务和 generation 管理；
- 实现低清预览、中心优先 tile、结果缓存；
- 将模型计算时间和 UI 显示时间分开测量；
- 在 Web 中接入 Mandelbrot 连续场画布；
- Tk 视图只修复取消和过期结果问题，不继续扩张功能。

完成标准：

- 连续缩放不会产生无限堆积的后台任务；
- 新视图不会被旧结果覆盖；
- 交互期间输入响应不被高质量计算阻塞；
- 清晰结果完成后，画面不会发生明显错位或跳回。

### Phase 4：WebGL 预览和三种视觉范式

**目标：** 将新架构从 Mandelbrot 扩展到三种不同模型。

工作项：

- Mandelbrot WebGL fragment shader；
- Life Game 网格画布和时间轴；
- N-body 粒子渲染、跟踪和暂停；
- 每种范式都有自己的 renderer protocol；
- 共享沉浸式外壳、HUD、抽屉和模式切换。

完成标准：

- 三个模型不依赖同一套三栏布局；
- 每个模型拥有符合自身特性的操作方式；
- 共享外壳代码不包含模型专用数学逻辑；
- WebGL 不可用时能够回退到 Canvas 或服务端结果。

### Phase 5：实验室能力和完整模型迁移

**目标：** 把现有 Tk 的研究能力逐步带到新 UI。

工作项：

- 批量统计和曲线扫描转为异步任务；
- 实验配置保存、复制和导出；
- 渗流模型迁移到网格实验范式；
- Buffon Needle 迁移到几何统计范式；
- Web 版本成为推荐入口；
- Tk 作为稳定的兼容和低依赖入口继续维护。

完成标准：

- 旧模型的主要研究功能在 Web 实验室中可用；
- CLI、Tk 和 Web 对同一模型的核心结果一致；
- 用户可以保存并复现实验配置；
- 没有迁移的模型仍可使用 generic fallback。

### Phase 6：桌面打包和深度能力评估

**目标：** 在体验和渲染架构稳定后，再决定发布形态。

候选方案：

- 继续使用本地浏览器；
- 使用 Tauri 打包 Web UI；
- 评估 PySide6/Qt Quick 是否有必要作为另一种桌面壳。

这一阶段才评估：

- GPU 兼容性；
- 离线打包；
- 自动更新；
- 深度缩放和高精度算法；
- Windows/macOS/Linux 发布方式。

## 9. 性能指标与验收标准

### 9.1 Mandelbrot 交互指标

第一版目标建议设为相对指标，避免绑定某一台机器：

| 指标 | 目标 |
| --- | --- |
| 拖动开始到画面响应 | 小于 50 ms 的预览反馈 |
| 连续滚轮 | 不出现窗口冻结或明显输入丢失 |
| 旧任务数量 | 同一视图最多一个活动高质量任务 |
| 预览到清晰图 | 先显示预览，再逐步细化 |
| 过期结果 | 不允许覆盖最新取景 |
| 画面错位 | 缩放、平移和窗口调整后不得出现系统性偏移 |
| 精度边界 | 达到可靠范围时有明确提示 |

### 9.2 通用体验指标

- 新用户无需阅读 README 即可完成一个模型的引导流程；
- 引导步骤必须显示“当前目标”和“为什么这样做”；
- 用户可以跳过引导并直接探索；
- 高级参数默认不打断主画面；
- 每个模型的主交互在首次进入时可见；
- 所有长任务都显示状态、可取消且不会阻塞导航。

### 9.3 质量门槛

每个迁移模型必须通过：

1. 纯模型单元测试；
2. handler/API 契约测试；
3. 引导步骤状态转换测试；
4. renderer 无头或浏览器自动化冒烟测试；
5. 交互性能基准；
6. 至少一个旧后端或 generic fallback 的回归测试。

## 10. 测试策略

### 10.1 模型层

继续使用当前金样本、固定随机种子和数学结论测试。UI 重构不得改变模型层输出，除非明确记录为数学行为变更。

### 10.2 体验层

新增纯 Python 测试覆盖：

- 引导步骤是否按顺序推进；
- 完成条件是否可重复判断；
- 跳过、重置和回退是否正确；
- 参数控制台打开后是否保持会话状态；
- 不同能力声明是否生成正确的可用动作。

### 10.3 渲染层

新增测试覆盖：

- 新 generation 是否取消或作废旧任务；
- tile 是否只写入对应取景；
- 取消后是否释放任务和缓存；
- 缩放锚点是否保持世界坐标不变；
- 预览图和最终图是否使用同一取景约定。

### 10.4 浏览器层

优先使用浏览器自动化覆盖关键路径：

```text
进入模型 → 开始引导 → 点击画布 → 下一步
        → 跳过引导 → 缩放 → 打开控制台
        → 修改参数 → 关闭控制台 → 重置
```

不要求第一阶段覆盖每个像素的视觉快照，但必须覆盖交互状态和错误状态。

## 11. 风险和取舍

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Web 前端引入第二种语言 | 构建和维护成本提高 | 先保持 Python API 稳定，只迁移三个垂直切片 |
| WebGL 设备兼容性 | 部分设备无法 GPU 预览 | Canvas / 服务端图像 / Tk fallback |
| 引导内容增加维护成本 | 每个模型都要设计教学流程 | 引导协议通用化，第一期只做三个模型 |
| 新旧 UI 并存 | 短期代码重复 | 明确 Web 为主、Tk 为兼容，不要求一次删除 |
| 后台任务取消不彻底 | CPU 峰值和内存压力 | 单活动任务、取消事件、generation 和压力测试 |
| 深度缩放精度不足 | 用户看到错误细节 | 明确提示，普通模式和高精度模式分开 |
| 过早打包桌面应用 | 把问题封装而不是解决 | 先完成浏览器体验，再选择 Tauri 或其他壳 |

---

## 12. 明确的非目标

第一阶段不做以下事情：

- 不重写全部数学模型；
- 不删除 Tk；
- 不立刻支持无限深度 Mandelbrot；
- 不为所有模型设计相同的控件面板；
- 不先开发完整的用户账户、云同步或在线模型市场；
- 不在没有性能基准的情况下盲目引入多进程、GPU 和任意精度库；
- 不为了“看起来现代”而添加与模型无关的动画和装饰。

## 14. 最终判断

项目不需要换掉所有东西，应该进行一次有边界的架构转向：

```text
现状：模型 + 参数表单 + 通用三栏视图
目标：模型内核 + 体验会话 + 视觉范式 + 沉浸式外壳 + 异步渲染
```

最重要的执行顺序是：

```text
先稳定模型契约
  → 再增加能力和体验协议
  → 再做 Mandelbrot 沉浸式 Web 垂直切片
  → 再做取消、分块和 GPU 预览
  → 最后迁移其它模型和桌面打包
```

这样既不会丢掉当前项目已经积累的数学正确性和测试资产，也能逐步摆脱“所有模型都是一个控制面板”的限制。
